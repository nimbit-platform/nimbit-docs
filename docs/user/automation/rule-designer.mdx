A rule watches data from your things. When a condition is met, it runs one or more actions: send an email, notify a channel, raise an event, call a webhook or update a measure.

You build a rule as a short chain of steps on a canvas. Each step is a node:

**Start** (which things) → **Condition** (what to check) → **Trigger** (when to fire) → **Actions** (what to do)

:::info What you need
- A role that may read rules to see **Automation › Rule Designer**, and one that may create rules to make new ones.
- A desktop browser. The rule canvas does not open on a phone.
- Things that already send data. See [First device to first dashboard](../../get-started/first-device.mdx).
:::

## Create a rule

1. Open **Automation › Rule Designer** and select **Create rule**.
2. In **Create new rule**, enter a **Name**. It must be unique in your tenant.
3. Optionally add a description and **Tags**. Tags help you find the rule in the list. They do not change what it does.
4. Save. The rule appears in the list as **Inactive**.
5. Select the rule name to open it.

The list shows each rule's **Status**, last modified date, **Version Count** and tags. Use the search box or the **Status** filter to narrow it down. To delete rules, select them in the list and use the delete action.

## Build the rule on the canvas

A new rule opens in edit mode with a **Start** node. Select a node to edit it in the side panel. Select the **+** below a node to add the next step. The **+** only offers steps that are valid at that point.

Your changes are saved automatically as a **draft**. The rule does not change until you apply the draft (see [Apply your changes](#apply-your-changes)).

### 1. Start: choose the things

The **Start** node decides which things the rule watches. Pick one of two contexts:

| Context | Use it when |
| --- | --- |
| **Thing type** | The rule is specific to one kind of device. It applies to every thing of that type, or to a hand-picked subset. |
| **Tags** | The rule should apply to a changing set of things across types. Enter a search expression and every thing whose tags match is included. |

:::info Update Measures needs a thing type
The **Update Measures** action is only available when the context is **Thing type**.
:::

### 2. Condition: what to check

The **Condition** node has two tabs.

**Simple**: pick a **Measure**, an **Operator** (for example **Greater than**) and a value. Select **Add condition** to combine several checks with **and** or **or**. For a measure you can also look at more than the current value. Under **Look at**, choose one of:

| Option | Meaning |
| --- | --- |
| **Current value** | The value just received. |
| **Average**, **Minimum**, **Maximum**, **Sum**, **Count** | Computed over a **Window** of time. |
| **Previous sample**, **Change from previous** | Compare with the sample before. |
| **Rising**, **Falling**, **Slope** | The direction of the values over the window. |

You can also **Compare with previous period** and set a **Minimum change**.

**Advanced**: write the condition yourself as a Grule `when` clause. The thing's data is available as `event`, for example `event.HasNumeric("temperature") && event.Numeric("temperature") > 30`. Select **Open editor**, write the expression, then **Test** to check it against a sample payload.

:::warning Simple and Advanced do not mix
While **Advanced** is selected, the **Simple** conditions are kept as a draft and are not evaluated.
:::

:::info Test uses a sample payload
**Test** reads window functions such as **Average** as missing, because it has no history. Test those on live data instead.
:::

### 3. Trigger: when to fire

The trigger decides how often the actions run while the condition holds.

| Trigger | What it does |
| --- | --- |
| **Default** | Runs the actions every time the condition is met. |
| **Duration** | Runs them only after the condition has held without a break for the **Duration** you set, for example 5 minutes. |
| **Consecutive Fulfillment** | Runs them after the condition was met in a set number of evaluations in a row (**Fulfillment Target**). |
| **Sleep** | Runs them once, then waits the **Sleep period (Seconds)** before it can fire again, even if the condition still holds. |
| **Toggle** | Runs them when the state changes. **Direction** is **In** (condition starts to hold), **Out** (stops holding) or **Every** (both). |

Some triggers also offer **First match only**: run the actions for the first match instead of every match.

:::tip Avoid a flood of messages
For alerts, use **Toggle** with **In**, or **Sleep**. With **Default**, you get a message for every value that meets the condition.
:::

### 4. Actions: what to do

After a trigger, add one or more actions.

| Action | What it does |
| --- | --- |
| **Notification** | Sends an in-app notification to chosen users and groups. You set a subject, **Severity** and **Message**. |
| **Notification channel** | Sends a message through the channels you choose, for example Slack, Teams, a webhook or ntfy. Set up channels first. |
| **Email** | Sends an email to users, groups or addresses. Plain text, or a **Mail Template**. |
| **Webhook** | Calls an external URL with the method, headers and authorisation you set. |
| **Event** | Creates an event of an **Event type** with a title and **Severity**. It appears under **Monitoring › Events**. |
| **Update Measures** | Writes values to measures of a thing type. |

Severity is one of **Info**, **Warning**, **Error** or **Critical**.

## Apply your changes

While you edit, a bar above the canvas switches between **Active** and **Draft** views. The icon next to the rule name shows whether the flow is valid. Hover it to read what is missing, for example that the graph needs an input and an output node.

| Control | What it does |
| --- | --- |
| **Publish** | Appears on a new rule. Publishes the first version. |
| **Apply draft** | Replaces the live version with your draft. Disabled while the rule is invalid. |
| **Reset draft** | Throws your draft away and goes back to the live version. |
| **Lock** / **Unlock** | Leaves or enters edit mode. |
| **Versions** | Opens the **Version overview**. Use **Create version** to keep the current state as a new version, and switch between versions. |
| **Activate** / **Deactivate** | Turns the rule on or off. |

The gear button (**Edit rule**) changes the name, description and tags.

## Test and turn on

1. Check the validity icon is green.
2. In the Advanced condition editor, use **Test** if you wrote an expression.
3. Select **Activate**. A message confirms it. The rule is now **Active** in the list.
4. Send data that meets the condition. If you have no device, open the thing and use **Simulate device**.
5. Check the result: an email arrives, a notification shows in the header, or an event appears under **Monitoring › Events**.

Only one version of a rule is active at a time. Activating a version switches off the version that was active. **Activate** uses the published version. It does not apply a pending draft, so select **Publish** first. If the version is already active, **Publish** puts your changes live at once.

Events that show which conditions of a rule matched are listed under **Monitoring › Events**. To stop a rule, select **Deactivate**. Nothing is deleted.

## Example: email me when the temperature is above 25 °C

This example uses the thing type `Room sensor` with a `temperature` measure from [First device to first dashboard](../../get-started/first-device.mdx).

:::warning Email goes through the Email action
The **Notification channel** action sends to the channels you create under **Configuration › Notification Channels**. In the channel form you can create Slack, Microsoft Teams, Webhook and ntfy channels, but not an email channel. For email, use the **Email** action below. The next section shows the channel variant.
:::

1. Open **Automation › Rule Designer** and select **Create rule**. Name it `Room too warm` and save.
2. Open the rule. On **Start**, choose **Thing type** and select `Room sensor`.
3. Select **+** and add a **Condition**. On the **Simple** tab, set **Measure** to `temperature`, **Operator** to **Greater than**, value `25`.
4. Select **+** and add a **Toggle** trigger. Set **Direction** to **In**. You get one email when the room becomes too warm, not one per reading.
5. Select **+** and add an **Email** action. Enter a **Subject** such as `Room too warm` and a **Body**. On **Users and Groups**, add yourself.
6. Check the validity icon, then select **Publish**, then **Activate**.
7. Open a `Room sensor` thing and use **Simulate device**, or send a temperature above 25. The email arrives shortly after.

The Email action sends through the tenant's own mail server if one is set up under [**Tenant settings**](../administration/tenant-settings.mdx), and otherwise through the platform mail server. If neither works, the mail is not sent and the failure is recorded as an event. See [Events](../monitoring/events.mdx).

**Subject** and **Body** accept placeholders in double curly braces. They are replaced when the mail is sent. ### Variant: send it to Slack, Teams, ntfy or a webhook

1. Open [**Configuration › Notification Channels**](../monitoring/notification-channels.mdx) and select **Create channel**.
2. Choose a **Channel type**, enter a **Name** and the target (for example the **Slack webhook URL**). Leave **Automatic routing** off so the channel only receives what a rule sends.
3. Select **Send test** to check it.
4. In step 5 of the example, add a **Notification channel** action instead of **Email**. Select your channel, then set a title, **Message** and **Severity**.

## When something does not work

| Problem | Check |
| --- | --- |
| The rule never fires | Is the rule **Active**? Is the thing in the **Start** context? Does the measure name match the thing type? |
| **Apply draft** is disabled | The flow is invalid. Hover the validity icon. Also, switch to the **Draft** view. |
| Too many messages | Use **Toggle** (**In**) or **Sleep** instead of **Default**. |
| **Update Measures** is missing | Change the **Start** context to **Thing type**. |
| The canvas does not open | Use a desktop browser. |
