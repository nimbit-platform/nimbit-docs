An event tells you something happened. An **incident** tells you a problem needs someone. It collects the related events, so an alarm that fires twenty times is one incident, not twenty. Someone acknowledges it, works on it and resolves it, and the page keeps the history.

Incidents open in two ways:

- **By a policy.** A policy decides which events open an incident and how they group. An administrator sets policies up. See [Incident configuration](./incident-configuration.mdx).
- **By hand.** Anyone with permission can report a problem.

Open **Monitoring › Incidents**. The menu entry shows the number of open incidents that nobody has acknowledged.

## The list

The status tabs show how many incidents are in each state.

| Tab | Shows |
| --- | --- |
| **Active** | Everything still being handled: open, acknowledged and in progress. This is the default. |
| **Unacknowledged** | Nobody has taken it yet |
| **Acknowledged** | Someone has seen it and owns it |
| **In progress** | Being worked on |
| **Resolved** | Fixed, waiting to be closed |
| **Closed** | Done, no more changes |
| **All** | Every incident |

Columns: **Incident**, **Severity**, **Subject**, **Status**, **Condition**, **Events**, **Assignee** and **Last event**. **Condition** says whether the alarm is still on (**Active now**) or when it **Cleared**. An incident gets a number such as `INC-1042`.

To narrow the list:

1. Search by title or incident number.
2. Use the filters: **Severity**, **Status**, **Policy**, **Assignee** and **Thing**.
3. Use **Assigned to me** to see yours, and **Watching** to see the ones you follow.

To act on several at once, tick the rows. A bar appears with **Acknowledge** and **Assign**. Incidents that cannot take the action are skipped, and a message tells you how many.

### Your first incident policy

If your tenant has no incident policies, an empty list says so. If you have permission, the page offers **Turn on a shipped policy**: ready-made policies for rule alarms, connectivity outages and geofence dwell. They ship switched off. Select **Turn on** next to one, or **Open policies** to see them all.

### Report a problem by hand

1. Select **New incident**.
2. Enter a **Title** and choose a **Severity**.
3. Choose the **Thing** the problem is about. With some roles this is required. Where it is optional, leave it empty for a site, a process or something you did not model, and name it under **About (optional)**.
4. Optionally add a **Description** and an **Assignee**, and fill in any custom fields.
5. Optionally link events of that thing from the last 24 hours with **Link events**. An event belongs to one incident only, and one that is already in another is refused.
6. Select **Create incident**.

A manual incident works like any other: assign, comment, resolve. You can also report one from a thing: **⋯ › Report a problem** on the [thing page](./thing-page.mdx).

### The workflow

An incident moves through these states:

**Open** → **Acknowledged** → **In progress** → **Resolved** → **Closed**

The header shows only the buttons that make sense now, and that your role allows.

| Button | When | What it does |
| --- | --- | --- |
| **Acknowledge** | Open | Marks that you have seen it |
| **Assign** | Open, acknowledged, in progress | Gives it to a person. Assigning an acknowledged incident moves it to in progress. **Assign to me** is the quick way. |
| **Resolve** | Open, acknowledged, in progress | Records the fix. You choose a resolution reason. |
| **Close** | Resolved | Ends it. |
| **Reopen** | Resolved or closed | Opens it again, until the reopen window passes |

The **⋯** menu has **Watch** or **Stop watching**, and **Edit title and severity**.

:::info Statuses have your names
Your administrator can rename statuses. They sit on top of the five fixed categories above. The buttons follow the category, so renaming never changes how the workflow behaves.
:::

### Resolve an incident

1. Select **Resolve**.
2. Choose a reason. If the list is empty, an administrator must add reasons first. See [Incident configuration](./incident-configuration.mdx#settings).
3. Fill in any custom fields marked **Required on resolve**.
4. Select **Resolve incident**.

If alarms are still active, the dialog warns you. Resolving records your decision. A matching event can reopen the incident.

Policies can also resolve an incident for you, for example when every alarm has cleared. The **Details** panel shows how it was resolved: **All episodes closed**, **Resolved manually**, **Resolved by an automation** or **Resolved by timeout**.

### What is on the page

- **Events**: the events in the incident. **Episodes** groups an alarm's open and close events. **All events** lists each one. You can remove an event you added by mistake. The event that opened the incident cannot be removed.
- **Activity**: every change and comment, in order, with who or what did it. Write a comment in **Add a comment**; Ctrl+Enter sends. Use **Comments** to show only comments.
- **Links**: things, knowledge documents, work orders, reports, dashboards or external pages related to the incident. Use **Add a link**.
- **Details**: status, assignee, severity, subject, who opened it, and the resolution.
- **Custom fields**: the extra fields your tenant records on every incident.
- **Watchers**: people who get every transition and comment. **Mute this incident** stops emails and notifications for you only.
- **Automations**: which automations ran for this incident. Shown if you may read policies.

On a phone, **Events**, **Activity** and **Links** are tabs.

### Severity

The severity of an incident follows its policy. By default it is the highest of its events and only rises. You can change it by hand with **Edit title and severity**.

### Reopening

A resolved incident stays open to reopening for a time set by its policy. A matching new event in that time reopens it by itself. After the time passes, the incident is closed and **Reopen** is gone. Report a new incident instead.

## What you can do depends on your role

| You can | Needs |
| --- | --- |
| See incidents | Read permission on incidents |
| Report, comment, watch | Create permission on incidents |
| Acknowledge, assign, edit, link, remove events | Update permission |
| Resolve, close, reopen | Update and execute permission |

If a button is missing, ask your administrator about your role.
