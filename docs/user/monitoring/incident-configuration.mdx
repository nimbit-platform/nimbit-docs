Without a policy, events never open incidents. People can still [report one by hand](./incidents.mdx#report-a-problem-by-hand). This page is for the administrator who sets policies up.

Open **Settings › Configuration › Incidents**. The page has two tabs: **Incident policies** and **Incident settings**. You need permission to read incident policies to see the entry, and to write them to change anything. Without write permission you see **You can view this configuration but not change it.**

## Incident policies

A policy answers four questions:

1. **Which events** open an incident?
2. **How are they grouped** into one incident?
3. **When** does the incident open, resolve and close?
4. **What happens** when it changes state? (automations)

An event joins the first active policy that matches it. Policies are checked by **priority**, lowest number first.

### Start with the shipped policies

Select **Import default policies**. IoT Breeze creates the shipped policies your tenant does not have yet. A policy you already have is left alone, so importing twice creates nothing new. **They arrive switched off.** Nothing opens until you turn one on.

| Policy | What it does |
| --- | --- |
| **Rule alarms per thing** | One incident per thing for the events its rules raise. Resolves when every alarm has cleared and ten quiet minutes have passed. Closes a day later. |
| **Connectivity outages** | One incident per thing that stays offline for five minutes. Resolves when the thing is back and five quiet minutes have passed. |
| **Geofence dwell** | One incident per fence and thing when a thing stays inside or outside a geofence for thirty minutes. Resolves when it leaves. |

Switch a policy on with the **Active** switch in the list.

### The list

Columns: **Name**, **Groups by**, **Resolves when**, **Origin** (**Shipped**, **Custom** or a pack), **Last match** and the open incidents. Search the list, or filter by active state and origin. Change a priority number to reorder policies. Dragging rows is not available. Use the row menu to **Duplicate** (the copy is inactive) or **Delete**. Deleting removes the policy and its automations. Incidents it opened stay, without a policy.

### Create or edit a policy

1. Select **New policy**, or open a policy.
2. Under **Name and priority**, enter a **Name** and a **Priority** from 0 to 10000.
3. Fill in the sections below.
4. Save. A line called **In short** sums up what the policy does.

#### Which events

An event matches when every clause holds. Leave a clause empty to ignore it.

| Clause | Meaning |
| --- | --- |
| **Event type names** | Patterns on the event type name. Whole name, any case, `*` matches any characters, for example `Door *`. |
| **Specific event types** | Pick event types of your tenant |
| **Minimum severity** | **Any severity**, or a severity and above |
| **Thing types** | Only events about things of these types |
| **Raised by** | What raised the event: **Rule engine**, **Geofence**, **Connectivity**, **API**, an action or **Repair**. None checked means any. |
| **Alarm going on / going off / single events** | An alarm going on is **Open**, going off is **Close**, anything else is a **Point** |
| **Payload conditions** | Conditions on the event data. Use a dotted path such as `sensor.name`, an operator (equals, does not equal, is greater than, is at least, is less than, is at most, contains, is one of, exists) and a value. Every condition must hold. |

#### Group into one incident by

Events about the same thing, type or value join one incident.

| Option | One incident per |
| --- | --- |
| **Thing** | Thing, for all its events |
| **Thing and rule** | Rule or fence on one thing |
| **Hierarchy level** | Site, hall or line. Pick the level. |
| **Thing type** | Thing type, across the fleet |
| **Event type** | Event type, tenant-wide |
| **Payload field** | Value of a field in the event data, for example `batch_id`. Enter the dotted path. |

#### Timing and resolution

| Setting | Meaning |
| --- | --- |
| **Open after** | Open only if the alarm is still on after this long. `0` opens at once. |
| **Quiet window** | No new event for this long before the incident can resolve |
| **Resolve when** | **Every episode closed (alarm off)**, **A matching event**, **Only by a person or an automation**, or **A timeout** |
| **Resolving event** | For **A matching event**: clauses that identify the event that resolves it |
| **Resolve after** | For **A timeout**: how long after opening it resolves |
| **Close after resolving** | A matching event in this time reopens the incident. `0` closes at once. |
| **Severity** | **Highest of its events, rises only**, or **Severity of the event that opened it** |
| **Title template** | The incident title. Insert **Event title**, **Thing name** or **Event type**. A preview shows the result. |

Durations can be set in seconds, minutes, hours or days. A duration can be at most 30 days; **Close after** at most one year.

:::tip Why a quiet window
A sensor that flaps on and off every minute raises many events. With a quiet window and **Close after resolving**, they stay one incident instead of many.
:::

## Automations

An automation runs an existing action once when an incident of a policy changes state. This is how you tell people about a problem once, even if the alarm flaps.

1. Open the policy and select **Edit automations**. Save the policy first if it is new.
2. Select **Add automation**.
3. Under **When the incident**, choose the transition.
4. Under **Run action**, pick an action. If you cannot run actions, you cannot create or change automations.
5. Set **Wait** if the transition needs it, and **Order** for several automations on one transition.
6. Select **Save automation**.

| Transition | Runs when the incident |
| --- | --- |
| **Opened** | is opened |
| **Escalated** | is escalated (severity rises) |
| **Acknowledged** | is acknowledged |
| **Unacknowledged for** | stays unacknowledged for the **Wait** time |
| **Resolved** | is resolved |
| **Reopened** | is reopened |
| **Timeout after** | is still open after the **Wait** time |

An escalation is two automations: **Unacknowledged for** 15 minutes runs a louder action, for example a message to a different channel.

Actions are not created here. Create them on an [event type](./event-types.mdx#add-an-action) or from a [notification channel](./notification-channels.mdx), then pick them. Event type actions run on every event. Automations run once per incident transition.

## Settings

**Incident settings** applies to every incident of the tenant.

### Statuses

Statuses are your own names on top of five fixed categories: **Open**, **Acknowledged**, **In progress**, **Resolved** and **Closed**. Automations and auto-resolution follow the category, so renaming a status never breaks them.

1. Select **Add status** in a category, or edit one.
2. Enter a name and a colour.
3. Optionally select **Default of its category**. Each category keeps exactly one active default.

A status cannot be deleted while incidents use it, and its category cannot change.

### Resolution reasons

The reasons a person picks when they resolve an incident. **Add resolution reason** creates one. People cannot resolve an incident until at least one reason exists. A reason in use cannot be deleted. Incidents resolved by a policy record **Condition cleared** or **Resolution event** instead.

### Custom fields

Extra fields on every incident, for what your team records, such as a root cause or a cost centre.

1. Select **Add field**.
2. Enter a **Label** and a **Key**. The key uses lower-case letters, digits and underscores, starting with a letter.
3. Choose the **Type**: **Text**, **Number**, **Choice**, **Date** or **User**. For **Choice**, add one option per line, as `value` or `value | label`.
4. Tick **Required when resolving** if people must fill it in before they resolve.

The key and type cannot change after creation. Changing **Required** only affects resolutions from then on. A field with values cannot be deleted.
