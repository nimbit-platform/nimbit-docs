Every thing has its own credentials. A device uses them to prove who it is, and IoT Breeze only accepts data from a device for that device's own thing. This page shows where to create the credentials and how a device sends data with them.

Open the thing (**Settings › Onboarding › Things**) and go to the **Connections** tab.

## The Connections tab

At the top, **Connection** shows a bar of the last 24 hours with connects and disconnects.

Below it, one block per connector. A thing whose thing type uses **Nimbit** has a **Nimbit** block. Each block has:

- **Connection info**: opens a drawer with everything a device needs to connect. See [Read the connection details](#read-the-connection-details).
- A switch that turns the connection on or off. If your tenant has switched the connector off, the switch is disabled and says so.

## Create credentials

The **Nimbit** block has three tiles. Each comes with a **Primary** and a **Secondary** key. Having two lets you rotate keys without downtime: move your devices to the secondary, then rotate the primary.

| Tile | Use it when |
| --- | --- |
| **Basic authentication** | The client only supports a username and password. The credentials never expire. |
| **JWT authentication** | You want a bearer token that expires. Validity is 30 days to 7 years. |
| **Device key** | You need to see or rotate the signing key behind the other two. |

### Basic authentication

1. Under **Basic authentication**, select **Primary · Generate credentials**.
2. Copy **Username** and **Password**.

Basic credentials do not expire. To invalidate them earlier, rotate the signing key under **Device key**.

### JWT authentication

1. Under **JWT authentication**, select **Primary · Generate token**.
2. Choose **Expires in** (a preset or a number of days). The hint shows the exact date.
3. Select **Generate token**.
4. Copy **Username**, **Token** and **Expires at**.

:::warning Copy the token now
Treat the token like a password. Anyone who holds it can act as the device until it expires or the signing key is rotated. The drawer clears when you close it. Select **Generate new token** if you lost it.
:::

### Device key

**Device key** holds the signing keys behind every token and basic credential of this thing. Select **View key** to see a key. Select **Rotate** to replace it: clients that still use the old key are refused from then on.

## Read the connection details

Select **Connection info**. The **Device connection** drawer shows these values, each with a copy button:

| Section | Field | Meaning |
| --- | --- | --- |
| **General** | **Gateway url** | The MQTT broker, for example `mqtt://host:1883`. A broker with TLS shows `mqtts://`. |
| | **Username** | The MQTT and HTTP user name of this thing. It is the same for every credential type. |
| | **Client id** | The MQTT client ID, or its required start. See below. |
| **Publish subjects** | **Telemetry** | The topic the device publishes data to. |
| **Subscribe subjects** | **Commands** | The topic the device listens on for commands. |
| | **Errors** | The topic that reports messages that were refused. |
| **REST** | five endpoints | URLs and example payloads for HTTP. |

Copy the values from here instead of composing them. They follow this pattern:

| Value | Pattern |
| --- | --- |
| Client ID | `<tenantId>:<deviceId>` |
| Telemetry topic | `tenant/<tenantId>/device/<deviceId>/telemetry` |
| Commands topic | `iot/tenant/<tenantId>/device/<deviceId>/cmd/#` |
| Errors topic | `iot/tenant/<tenantId>/device/<deviceId>/error` |

## Send data

<Tabs groupId="send-data">
<TabItem value="mqtt" label="MQTT" default>

Connect to the **Gateway url** from Connection info (port 1883, or 8883 for `mqtts`).

| Setting | Value |
| --- | --- |
| Client ID | `<tenantId>:<deviceId>`, as **Client id** shows it. You may add a suffix: `<tenantId>:<deviceId>:<suffix>`. Any other client ID is refused. Always send one: an empty client ID is not accepted. |
| Username | **Username** from Connection info. |
| Password | The basic **Password**, or the JWT **Token**. |
| Publish to | The **Telemetry** topic. |
| Subscribe to | The **Commands** and **Errors** topics, if you need them. |

The payload is a JSON object:

```json
{
  "thingType": "room_sensor",
  "data": {
    "temperature": 22.5,
    "humidity": 61.3
  },
  "time": "2026-11-07T09:30:00Z",
  "geo": { "latitude": 52.52, "longitude": 13.405 },
  "tags": { "location": "warehouse-A" }
}
```

| Field | Required | Meaning |
| --- | --- | --- |
| `thingType` | Yes | The **Name** or ID of the thing's thing type. |
| `data` | Yes, unless `geo` is set | Measure values by measure name. At least one value must not be `null`. |
| `geo` | No | `latitude` and `longitude`, and optionally altitude, heading and speed. |
| `time` | No | When the values were measured, in ISO 8601 with a time zone. Without it, the time of arrival is used. |
| `tags` | No | Extra labels for the message. |
| `tenant`, `id` | No | If you send them, they must match the topic. |

```bash
mosquitto_pub -h <mqtt-host> -p 1883 \
  -i "<tenantId>:<deviceId>" \
  -u "<username>" -P "<password-or-token>" \
  -t "tenant/<tenantId>/device/<deviceId>/telemetry" \
  -m '{"thingType":"room_sensor","data":{"temperature":22.5}}'
```

{/* TODO: verify that a message without `time` is stamped with its arrival time, and what `tags` do to stored rows. */}

A device can only publish to its own telemetry topic and only subscribe to its own commands and errors topics. Commands arrive at QoS 0: a command is not queued for a device that is offline.

Changing or rotating a key stops new logins with the old credentials. It does not end a connection that is already open. Disconnect the device to apply it.

</TabItem>
<TabItem value="http" label="HTTP">

Send a `POST` with a JSON body to an endpoint under **REST** in Connection info. Authenticate with the same credentials as MQTT, in the `Authorization` header:

| Credential | Header |
| --- | --- |
| Basic | `Authorization: Basic <base64 of username:password>` |
| JWT | `Authorization: Bearer <token>` |

```bash
curl -X POST "<ingest-url>/api/v1/message/structured" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "tenant": "<tenantId>",
    "thingType": "room_sensor",
    "id": "<deviceId>",
    "data": { "temperature": 22.5, "humidity": 61.3 }
  }'
```

With basic credentials, let curl do the encoding: `-u "<username>:<password>"`.

The message has the same fields as the MQTT payload. The `tenant` and `id` must match the credential. A message for another device is refused.

| Endpoint | Use it for |
| --- | --- |
| **Structured JSON** (`/api/v1/message/structured`) | One message or a list of messages. The answer says whether they were stored. |
| **Async structured JSON** (`/api/v1/message/async-structured`) | The same, for senders that do not wait for the result. |
| **Line protocol** (`/api/v1/write/line-protocol`) | InfluxDB line protocol. |
| **InfluxDB v2 compatible write** (`/api/v2/write`) | Tools that already write to InfluxDB v2. |
| **InfluxDB v1 compatible write** (`/write`) | Tools that already write to InfluxDB v1. |

The two InfluxDB endpoints sit at the root of the host, the others under `/tsflux`. Copy the full URLs from Connection info.

| Response | Meaning |
| --- | --- |
| 200 | Accepted. |
| 207 | Several messages: each failed one is listed with its index and reason. |
| 400 | The request was invalid. |
| 401 | The credentials are missing, wrong or expired. |
| 422 | The message will never be accepted, for example an unknown thing or no data. |
| 503 | Busy. Try again after the time in `Retry-After`. |

A `200` means the message was valid and accepted. It can take a moment until it appears in charts.

## Check that data arrives

- Open the thing. The **Overview** shows **Last signal** and **Live values**. **No signal yet** means nothing has arrived.
- Subscribe to the **Errors** topic. Every message that was refused for good is published there with the reason.
- Check the host, port, client ID and username against Connection info. A wrong client ID is the most common cause of a refused MQTT connection.
- Check that the measure exists in the **published** schema of the [thing type](./thing-types.mdx#drafts-publishing-and-versions), or turn on **Auto Schema Evolution**.
