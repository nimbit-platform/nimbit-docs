Serve selected things as Asset Administration Shells (AAS): a read-only API in the structure of IDTA Part 2, and AASX packages to hand over as files. Only things you expose one by one are served, and only to callers who may read them in IoT Breeze.

The API is compatible with the read profiles of IDTA Part 2 v3.2 that it lists at `/description`. It is checked against IDTA's published schemas and test tooling. It is not certified.

## What a shell contains

| Submodel | IDTA template | Published for | When |
| --- | --- | --- | --- |
| Nameplate | 02006-3-0 Digital Nameplate | Device things | Always |
| TechnicalData | 02003 Technical Data | Device things | Always |
| HandoverDocumentation | 02004-2-0 (VDI 2770) | Device and aggregate things | The thing has documents with a VDI 2770 class |
| TimeSeries | 02008-1-1 Time Series Data | Device and aggregate things | The thing has measures |
| CarbonFootprint | 02023 Carbon Footprint 1.0.3 | Any exposed thing | Its values are set and complete |
| HierarchicalStructures | 02011 | Aggregate things | Always; lists the members that are themselves exposed and readable |

## Before you start

- To expose a thing you need the **Aas** update permission. **Admin** and **System Admin** have it. **Manager** and **Viewer** can read shells but not expose things.
- A tenant admin turns the feature on (step 1).
- Classifying documents needs the Knowledge module, and permission to attach documents to the thing's record there.

## Steps

1. **Turn the feature on.** Open **Administration › Tenant Settings › Features**, switch on **Asset Administration Shell** and save. Optionally [set your defaults](#set-your-defaults) for the nameplate. You can prepare everything below while the feature is off. Nothing is served until it is on.
2. **Prepare the thing type.** Install the `aas-essentials` pack under **Administration › Tenant Settings › Packs**. It is not installed automatically. Add the `aas-exposure` interface to the thing type, plus `aas-digital-nameplate`, `aas-technical-data` and `aas-carbon-footprint` as you need them. An aggregate type cannot attach interfaces, so declare `aasEnabled` and the carbon footprint properties on it directly.
3. **Expose the thing.** Open the thing. On **Overview**, under **Asset Administration Shell**, switch on **Expose as Asset Administration Shell**. A default value on the thing type never exposes a thing: each thing is exposed by itself, by someone with the **Aas** update permission.
4. **Fill in the nameplate and technical data.** Set the values on the thing, or as initial values on the type. Only elements with a value are published. If you leave out an element the template requires, such as `OrderCodeOfManufacturer` or the address parts `Street`, `Zipcode`, `CityTown` and `NationalCode`, the submodel is published without it. A tool that checks against the template then reports the gap. The manufacturer name comes from the thing, else the tenant default, else the tenant's name.
5. **Add a carbon footprint.** With `aas-carbon-footprint` on the type, set the values as the type's initial values (one footprint for the product type) or on each thing. Calculation method, CO2 equivalent, reference unit, quantity, life cycle phase and publication date are required. The method, unit and phase take only the values of the IDTA template's lists, such as `ISO 14067`, `kg` and `A1-A3`. If one required value is missing or invalid, the whole CarbonFootprint submodel is withheld until you complete it.
6. **Add handover documents.** Attach the documents to the thing in Knowledge and [classify them](#classify-documents-for-the-handover-documentation). Only documents with a VDI 2770 Blatt 1:2020 class are published. Documents without a class, with another classification system, and files only placed in the thing's folder are not. The submodel says how many were left out, not which.
7. **Give your integration access.** Create an API key with the scope `aas:read`, as described in [Create an API key](../administer/api-key.mdx). Add `telemetry:read` if it needs time series values. An `aas:read`-only key reads the AAS API and nothing else in IoT Breeze.

## Set your defaults

The Digital Nameplate and the Handover Documentation use these values for every thing that sets none of its own.

1. Open **Administration › Tenant Settings › Features**. With **Asset Administration Shell** on, its section shows **Defaults for published shells**.
2. Enter a **Manufacturer name**, a **Contact e-mail** and a **Contact URL**. Each is optional. Without a manufacturer name, the tenant's name is used.
3. Save.

**Shell identifiers** shows the base of your shells' identifiers. It is read-only: changing it gives every published shell a new identifier, so only Nimbit support sets it.

## Classify documents for the Handover Documentation

A document is published in a thing's Handover Documentation only once it has a VDI 2770 Blatt 1:2020 class. Anyone who can attach documents to the thing's record can classify them.

1. Open **Knowledge › Explore**, select the thing and open the **Documents** tab. A banner says how many of the thing's documents are published.
2. An unclassified document says **Not published in the AAS until it has a VDI 2770 class.** Select **Classify**. For a classified one, choose **Edit classification…** in the row menu.
3. Choose one of the twelve classes. They come in four groups: 01 Identification, 02 Technical characteristics, 03 Activity-related documents and 04 Contractual documents. For example, an operating manual is `03-02` Operation.
4. Check the title. It starts as the file name and is published as the document's title.
5. Choose the document's language, one of the 24 official EU languages.
6. Select **Save**.

The row then shows the class, such as **03-02 Operation**, and the language. To take a document out of the Handover Documentation again, open the dialog and select **Remove classification**.

## Read shells with an API key

The base URL is `https://<host>/ocb/aas/v3`, on the host you open IoT Breeze on. Send the key as the bearer, or exchange it first for a token with `resource=nimbit:ocb` (see [API key exchange](../api/authentication.mdx#api-key-exchange)).

Shell and submodel ids in paths are base64url-encoded:

```bash
# Which profiles the server serves
curl -H "Authorization: Bearer <api-key>" "https://<host>/ocb/aas/v3/description"

# All shells you may read
curl -H "Authorization: Bearer <api-key>" "https://<host>/ocb/aas/v3/shells"

# One submodel, by its base64url-encoded id
curl -H "Authorization: Bearer <api-key>" "https://<host>/ocb/aas/v3/submodels/<base64url-submodel-id>"
```

Lists are paged. Continue with the `cursor` from `paging_metadata`. A page can be short, even empty, and still have a cursor.

## Export an AASX package

`GET /ocb/aas/v3/serialization?format=aasx` returns an AASX package (`application/aas+zip`). Without `format=aasx` you get the same environment as JSON. Name what to export with `aasIds` and `submodelIds`, at most 100 ids each.

- Documents up to 5 MiB each and 25 MiB per package are embedded. A larger one keeps a link to the API instead.
- One server builds at most 4 exports at once, and at most 2 per tenant. Another request gets `429` with `Retry-After: 10`. Try again then.
- An export without ids covers at most 500 shells. Above that it answers `400` and asks for filters.

## Registry and discovery

For integrators who find shells through a registry, the same base URL serves the read-only AAS Registry, Submodel Registry and Discovery routes of IDTA Part 2 v3.2: `/shell-descriptors`, `/submodel-descriptors`, `POST /lookup/shellsByAssetLink` and `/lookup/shells/{aasId}`. Descriptors are built from the shells you can read, so a thing appears in the registry exactly when it appears in the repository. Nothing can be registered or changed.

## Who sees what

- Shells are never public. Every request needs a signed-in user or an API key.
- A caller sees only exposed things they may read in IoT Breeze anyway. Others answer `404`. Gateway credentials are refused.
- Private properties and measures are never published, nor are values a private one reads through a proxy. A calculated measure that reads a private measure, or members of an aggregate the caller cannot see, is withheld and named under `WithheldMeasures`.
- The organization or site group a thing belongs to is never published.

## Limits

- The API is read-only.
- A paged request reads at most 2000 exposed things to fill a page.
- HandoverDocumentation lists at most 200 classified documents per thing, and then says it is truncated.
- A time series request serves at most 10,080 buckets and 200,000 values.
