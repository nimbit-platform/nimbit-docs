Connect a device that speaks MQTT, such as an eWON Flexy, with one credential for the gateway and send data for several things through it. For how membership and scope work, read [How gateways work](./how-gateways-work.mdx).

## Before you start

- You need the **Gateway** permission (the built-in **Admin** role has it).
- The device can connect with MQTT 3.1.1, a username and password, and a client ID you choose. The broker accepts QoS 0 and 1, not 2.
- Each device behind the gateway is a thing of your organization, or you can [register](../model/register-thing.mdx) it now. Its thing type has the measures you will send.

## Add the gateway

1. Open **Settings › Onboarding › Gateways** and select **Add gateway**.
2. Under **Type**, choose **MQTT device**.
3. Enter a **Name**. Leave **Namespace** empty, or type one.
4. Under **Config file format**, choose **Environment file (.env)**, **JSON (.json)** or **eWON Flexy BASIC parameters (.bas)**. The credential is the same in every format.
5. Select **Add gateway**.

IoT Breeze shows **MQTT credential for** the gateway name. Copy the **Password** or select **Download config** now. The password is shown once; a file you download later holds a placeholder instead.

The result lists these rows. Copy them from the screen rather than building them by hand.

| Row | Use |
| --- | --- |
| **Host**, **Port**, **TLS** | The broker. **On (mqtts)** means the listener wants TLS. |
| **Username**, **Password** | The credential. |
| **Client ID prefix** | `<tenant>:gateway:<gateway id>`. Use it as the client ID, or add `:<suffix>`. The broker refuses any other client ID. |
| **Topic prefix** | Every topic you publish on starts with it. |
| **Telemetry topic** | Publish one thing's data here. |
| **Batch topic** | Publish an array of things' data here. |
| **Status topic** | Publish the gateway's own health here. |

For an eWON Flexy, the **.bas** file holds these values as BASIC parameters. The BASIC program that reads them and publishes your tags is available on request from NimBit support at [info@nimbit.de](mailto:info@nimbit.de).

## Put things on the gateway

A gateway can send only for things that belong to it, and its messages never create things.

1. Create the things in IoT Breeze, if they don't exist.
2. Open the gateway, select the **Things** tab and select **Assign things**. Search for the things and select **Assign**. Or open a thing, edit it and choose the gateway in **Gateway**.

A thing is on at most one gateway. Assigning a thing that is on another gateway moves it.

## Publish data

Connect with the credential, then publish JSON.

<Tabs groupId="gateway-publish">
<TabItem value="thing" label="One thing per message" default>

Publish to the **Telemetry topic**, replacing `<thing>` with the thing's ID or alternate ID:

```text
tenant/<tenant>/gateway/<gateway id>/device/<thing>/telemetry
```

```json
{
  "thingType": "pump",
  "time": "2026-11-06T10:15:00Z",
  "data": { "pressure": 4.18, "running": true }
}
```

</TabItem>
<TabItem value="batch" label="One batch for several things">

Publish to the **Batch topic** an array with one element per thing. Each element names its thing with `id`:

```text
tenant/<tenant>/gateway/<gateway id>/telemetry
```

```json
[
  { "id": "pump-1", "thingType": "pump", "time": "2026-11-06T10:15:00Z", "data": { "pressure": 4.18 } },
  { "id": "tank-3", "thingType": "tank", "data": { "level": 0.62 } }
]
```

A batch can hold 500 elements and 1 MiB. A larger publish is dropped whole. A bad element is dropped alone. Leave out a device you can't reach instead of re-sending its last values: each stored element keeps its own thing online.

</TabItem>
</Tabs>

`thingType` is the thing type's name or ID. Leave out `time` to use the arrival time. Measure names and the full message rules are in [Message format](../connect/message-format.mdx).

Every 5 minutes, publish the gateway's own health to the **Status topic**:

```json
{
  "thingType": "mqtt_gateway",
  "time": "2026-11-06T10:15:00Z",
  "data": { "uptime_s": 5400, "buffer_used_pct": 0, "buffer_oldest_s": 0, "errors_per_min": 0, "clock_offset_ms": 0 }
}
```

The gateway turns **Online** with the first message and **Offline** after three missed ones.

## Check that it worked

Open the gateway. The **Health** tab shows **Online**, and the **Traffic** card shows **Messages per minute** and **Things active**, within a minute or two of the first data. Open one of the things: its latest values are there.

## If it doesn't work

- **The broker refuses the connection**: check the client ID against **Client ID prefix**, and that you copied the password completely. Lost it? Select **New credential** from the row menu; the old credential stops working for new connections at once.
- **A publish is acknowledged but nothing is stored**: the topic is outside the gateway's **Topic prefix**. The broker acknowledges a QoS 1 publish it then drops.
- **Traffic shows discards**: **Discards per minute** names the reasons. `not_member` means the thing isn't assigned to this gateway. `unknown_thing` means the thing or its thing type doesn't exist. `id_missing` means a batch element has no `id`.
- **The gateway stays Offline while data arrives**: only its own health message makes it online. Publish to the **Status topic**.
