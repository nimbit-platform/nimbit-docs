Die Berechtigungen der vier Systemrollen in jedem Tenant, je Ressourcentyp. Rollen legen fest, welche Art von Aktion erlaubt ist. [Gruppen](./access.mdx) legen fest, auf welchen Things.

## Die Tabellen lesen {#reading-the-tables}

| Buchstabe | Aktion | Spalte der Matrix |
| --- | --- | --- |
| `c` | Erstellen | **Erstellen** |
| `r` | Lesen | **Gelesen** |
| `u` | Aktualisieren | **Aktualisieren** |
| `d` | Löschen | **Löschen** |
| `x` | Ausführen | **Ausführen** |

Ein Strich bedeutet, dass die Rolle auf diese Ressource keine Berechtigung hat. Die Ressourcennamen sind so geschrieben, wie die Berechtigungsmatrix unter **Personen & Zugriff › Rollen** sie zeigt. Systemrollen lassen sich nicht ändern. Ein Benutzer mit mehreren Rollen hat alle ihre Berechtigungen zusammen.

## Was die Buchstaben bei manchen Ressourcen bedeuten {#what-the-letters-mean-for-some-resources}

| Ressource | Bedeutung |
| --- | --- |
| Aktion | `x` führt eine Aktion aus, etwa einen Befehl an ein Thing. |
| VNC-Server | `x` öffnet eine VNC-Verbindung. |
| Knowledge | `r` liest den Knowledge-Graphen und seine Dokumente. `c`, `u` und `d` erstellen, ändern und löschen Datensätze und die Knowledge-Einrichtung. `x` fragt Nimble und nutzt die MCP-Tools. |
| Vorfall | `c` erstellt einen Vorfall von Hand. `x` löst Vorfälle auf und führt sie zusammen. Nur Administrator darf löschen. |
| Vorfallsrichtlinie | Dieselben Buchstaben, für die Richtlinien und Automatisierungen, die Vorfälle eröffnen, und für Vorfallsstatus, Lösungsgründe und eigene Felder. |
| ApiKey | `c` erstellt einen Schlüssel, `r` listet die Schlüssel des Tenants, `u` ändert einen Schlüssel oder die Schlüsselrichtlinie, `d` widerruft einen Schlüssel. Das `c` des Modellierers gilt für persönliche Schlüssel. |
| Gateway | `r` listet Gateways und ihre Schlüssel, `c` erstellt eines, `u` stellt einen Onboarding-Code aus oder widerruft einen Schlüssel, `d` entfernt eines. |

## Hinweise zu den Systemrollen {#notes-on-the-system-roles}

| Rolle | Hinweis |
| --- | --- |
| **Administrator** | Einzige Rolle mit Einladung, Theme, ApiKey, ServiceAccount, Gateway, Datenlöschung und Prüfprotokoll. Hat keine Erstellen-Berechtigung für Benutzer und Tenant; Personen kommen über Einladungen dazu. |
| **Manager** | Liest Berichte, kann sie aber nicht erstellen oder ändern. Bearbeitet Vorfälle und liest Vorfallsrichtlinien. |
| **Modellierer** | Hat keine Berechtigung für Regel, Ziel, Arbeit, Vorfall, Aas oder Passport. Aas oder Passport vergeben Sie ausdrücklich über eine benutzerdefinierte Rolle. |
| **Viewer** | Dashboards sind schreibgeschützt: Ein Viewer kann sie nicht erstellen oder ändern. Darf Vorfälle erstellen, Aktionen ausführen, VNC-Verbindungen öffnen und Nimble fragen. Behält `crud` auf Abfrage. |

Ältere Installationen zeigen möglicherweise auch Rollen aus einer früheren Benutzerverwaltung, etwa **System Admin**, **Invitation** oder **Theme Designer**. Sie erscheinen als benutzerdefinierte Rollen. **System Admin** hat wie **Administrator** `ru` auf Aas und Passport.

## Benutzerdefinierte Rollen {#custom-roles}

| Regel | Detail |
| --- | --- |
| Typ | Wird in der Spalte **Typ** als **Benutzerdefiniert** angezeigt. Systemrollen zeigen **System**. |
| Vergabe | Sie können nur Berechtigungen ankreuzen, die Sie selbst haben. Die anderen sind gesperrt. |
| Ändern oder löschen | Nur ein Mitglied, das alle Berechtigungen der Rolle hat, kann sie ändern oder löschen. |
| Löschen | Benutzer, die die Rolle hatten, verlieren ihre Berechtigungen. |
